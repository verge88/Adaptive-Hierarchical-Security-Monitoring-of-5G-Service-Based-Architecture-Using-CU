# Stage39: KIE, причинный потоковый контроль и закрытие границ Stage38

Stage39 не изменяет замороженные исходные данные и детектор Stage38. Это отдельный слой реализации,
который переводит несколько пунктов из раздела ограничений и будущих работ статьи в исполняемые
проверки GitHub Actions.

## Что реализовано

### 1. КИЕ стала исполняемым протоколом контроля

`research/stage39_kie.py` реализует `KIERequest` и `KIEResponse`.

Запрос содержит:

- версию и направление `KIE_REQUEST`;
- идентификаторы контролирующего контура и контролируемого слота;
- монотонный номер цикла;
- метку времени;
- 128-битный случайный nonce;
- SHA-256 независимой политики полного профиля;
- SHA-256 текущего пакета телеметрии;
- HMAC-SHA256 над каноническим сообщением.

Ответ `KIE_RESPONSE` связан с исходным cycle/nonce и содержит заверенный отчётный блок.
В CI проверяются изменение содержимого, неправильная привязка ответа, устаревшая метка,
повтор cycle и повтор nonce. Таким образом КИЕ больше не является только методологическим
описанием разделения каналов.

### 2. Якорь свежести и восстановление

`FreshnessAnchor` хранит последний принятый cycle и хеши nonce на диске. После перезапуска
повтор ранее принятой КИЕ остаётся отклонённым. Добавлено отдельное HMAC-запечатанное зеркало:
при потере основного файла состояние восстанавливается из зеркала и replay по-прежнему отвергается.

Это проверяет отказ и восстановление одной копии якоря. Одновременная потеря основного состояния
и зеркала всё ещё требует внешней процедуры восстановления и не объявляется решённой аппаратной
задачей.

### 3. Независимая политика полного профиля

`stage39/full_profile_policy.json` задаётся отдельно от наблюдений NRF. Она содержит разрешённые:

- тип NF;
- адрес;
- FQDN;
- сервисы, версии, схему и сервисные endpoints.

Политика покрывает NSSF, AUSF, BSF, UDM, AMF, SMF, PCF, NRF и SCP. Это закрывает логическую
слепую область Stage38, где FQDN и nfServices зависели от эталона NRF.

Важно: для AMF/SMF/PCF/NRF/SCP Stage39 пока выполняет policy-level CI-моделирование. Это не новый
нативный эксперимент Open5GS с отдельными живыми экземплярами всех этих NF.

### 4. Потоковая проверка без будущего post-reference

`StreamRelationalVerifier` не получает будущий снимок после перехода. Во время stop/start/restart
он использует:

- текущую независимо заданную политику;
- известную операцию жизненного цикла;
- текущий witness;
- последнее причинно доступное состояние активности слотов.

Для изменяемого слота временное отсутствие допустимо только внутри перехода. Стабильные слоты
обязаны оставаться корректными. После restart новый UUID разрешается только при полном совпадении
семантики с политикой и текущим witness.

### 5. Граница duplicate nfInstanceId

Точный повтор одного `nfInstanceId` теперь отклоняется всегда, в том числе для изменяемого типа
в переходном окне. Для нескольких записей одного логического слота дополнительно формируется
`ambiguous_slot`.

### 6. Персистентное отравление реестра

В CI есть файловый `PersistentRegistry`. Проверка:

1. записывает чистое состояние;
2. изменяет сохранённый профиль;
3. повторно открывает реестр;
4. проверяет уже персистентно изменённое состояние.

Так как сравнение идёт с отдельной полной политикой, подмена FQDN/services после повторного открытия
обнаруживается. Это программный тест семантики персистентного отравления; он не является новой
эксплуатацией внутренней БД Open5GS NRF.

### 7. Измерение attack-to-alert latency

Для каждого из шести семейств мутаций измеряется время от момента передачи атакованного профиля
в потоковый verifier до получения списка тревог. JSON-артефакт содержит отдельные выборки,
median, p95 и max.

Это именно задержка нового in-process verifier в CI. Она не подменяет собой сетевую end-to-end
задержку промышленного 5G Core.

### 8. mTLS и OAuth2 client_credentials

`research/stage39_transport_probe.py` в GitHub Actions:

- создаёт временный CA, серверный и клиентский сертификаты OpenSSL;
- запускает локальный HTTPS endpoint с обязательным клиентским сертификатом;
- отклоняет клиента без сертификата;
- реализует тестовый OAuth2 client_credentials token endpoint;
- отклоняет неправильный client secret и неправильный bearer token;
- принимает корректный mTLS + bearer flow.

Сертификаты и credentials существуют только внутри CI.

### 9. SEPP-like граничная защита

Тот же transport probe проверяет защищённый междоменный envelope с source/destination PLMN,
nonce, digest полезной нагрузки и MAC. Изменение payload или destination отклоняется.

Это функциональная проверка свойства граничной целостности. Она **не является** реализацией
3GPP N32 и не заявляется как SEPP conformance test.

### 10. Длительный soak

`.github/workflows/stage39-soak.yml` запускается вручную с параметром 1–360 минут и по расписанию
раз в месяц с 30-минутным чистым прогоном. Отчёт фиксирует число итераций и ложных тревог.

Основной workflow использует короткий soak, чтобы PR-проверка не занимала десятки минут.

## GitHub Actions

Основной workflow: `.github/workflows/stage39-kie-integrity.yml`.

Он выполняет последовательно:

1. unit/boundary tests;
2. KIE request/response + anti-replay;
3. причинный lifecycle verifier без post-reference;
4. шесть семейств подмен;
5. персистентное отравление файлового реестра;
6. восстановление freshness anchor из sealed mirror;
7. mTLS + OAuth2 client_credentials;
8. SEPP-like edge integrity;
9. формирование `stage39_report.json`, `stage39_report.md` и
   `transport_security_report.json`;
10. публикацию артефакта `stage39-kie-streaming-evidence`.

Локальный эквивалент:

```bash
python -m unittest discover -s research -p 'test_stage39_kie.py' -v
python research/stage39_kie.py \
  --policy stage39/full_profile_policy.json \
  --output stage39_out \
  --soak-seconds 10
python research/stage39_transport_probe.py --output stage39_out
```

## Научная граница результата

Stage39 закрывает перечисленные логические и CI-проверяемые границы, но не превращает их автоматически
в доказательство промышленной защищённости. В частности, остаются отдельными задачами:

- живой эксперимент Open5GS для AMF/SMF/PCF/NRF/SCP как контролируемых объектов;
- аппаратная или физически независимая аттестация witness/policy;
- стандартное 3GPP SEPP/N32 interoperability/conformance testing;
- end-to-end latency на реальной сети с очередями, HTTP/2 и TLS;
- защита при одновременной потере всех копий freshness anchor;
- многочасовые/многосуточные прогоны, если они не были реально выполнены соответствующим Actions run.

Поэтому артефакты workflow должны интерпретироваться как воспроизводимая реализация и проверка
новых механизмов, а не как расширение численных результатов замороженного Stage38 без нового
нативного эксперимента.
