# Stage46 — устойчивость к компрометации одного группового проверяющего

## Цель
Проверить, сохраняется ли корректность иерархического решения, если одна из реплик
группового проверяющего полностью скомпрометирована и формирует ложную сводку,
аутентифицированную собственным действительным ключом.

## Архитектурное изменение
Каждая из четырех логических групп проверяется тремя независимо запускаемыми
GitHub-hosted jobs. Для каждой группы координатор принимает решение только при
совпадении не менее двух из трех нормализованных сводок. Каждая verifier-job
генерирует собственный случайный 256-битный HMAC-ключ; общий код не позволяет
вычислить ключи соседних реплик. GitHub artifact/job integrity используется как
связь отчета с соответствующей job; аппаратная аттестация не заявляется.

## Эксперимент
Источник данных — неизменяемый Stage44 seed, сформированный из Stage42 live
Open5GS evidence. Проверялись масштабы 13, 1040 и 4160 логических NF, четыре
детерминированных испытания на размер, штатный и атакованный режимы: всего 24
глобальных случая и 96 group-case решений.

В каждом group-case одна из трех реплик выбиралась как Byzantine. В штатном
случае она добавляла ложное предупреждение, а в атакованном подавляла локальные
предупреждения. Ложная сводка подписывалась ключом самой скомпрометированной
реплики, то есть проверка HMAC сама по себе не могла отличить ее от честной.

## Подтвержденные результаты
GitHub Actions run: 40687450694, conclusion=success.

- 24/24 глобальных решений после кворума точно совпали с централизованным пересчетом.
- 12/12 атакованных случаев были обнаружены.
- 0/12 штатных случаев дали ложное предупреждение.
- Обработано 288 аутентифицированных сводок, из них 96 сформированы Byzantine-репликами.
- В 86 из 96 group-case возникло фактическое расхождение голосов; во всех 86 случаях
  корректное решение восстановлено кворумом 2/3.
- Неверная подпись отклоняется.
- Отсутствие одной реплики допускается при совпадении двух оставшихся.
- Отсутствие двух реплик приводит к fail-closed результату.
- Контрольный опыт подтвердил предел схемы: две согласованно скомпрометированные
  реплики одной группы способны сформировать ложное большинство 2/3.
- 12 verifier jobs получили 12 различных runner_name. GitHub документирует
  стандартные ubuntu-24.04 jobs как новые VM, но физическая принадлежность этих VM
  не раскрывается и не может считаться подтвержденной этим опытом.

## Вывод для статьи
После введения трехкратного независимого исполнения групповой проверки и кворума
2/3 система сохраняет эквивалентность централизованной проверке при компрометации
одной verifier-реплики на группу в исследованной модели отказов. Это закрывает
прежний пробел только для f=1 Byzantine-компрометации и не распространяется на
две сговорившиеся реплики, компрометацию общего источника исходных данных,
координатора или на доказательство размещения на разных физических серверах.

Для строгого подтверждения физического разнесения требуется повторить тот же
workflow на self-hosted runners, заранее размещенных на независимых физических
узлах или независимых cloud instances с подтверждаемой инфраструктурной
идентичностью.
